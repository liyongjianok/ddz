# 网页版斗地主产品需求文档

## 1. 产品愿景

开发一个可用于真实研发流程的网页版斗地主棋牌游戏。项目不是一次性 Demo，而是一个可以让 ChatGPT、Claude Code、Codex 等 AI 编程工具按模块、按 Sprint 逐步实现的工程系统。

首个版本目标：

- 浏览器直接游玩。
- 实时多人房间。
- 支持真人玩家和机器人补位。
- 服务端权威的确定性规则引擎。
- 支持断线重连和刷新恢复。
- 对局记录可审计、可回放。
- 为后续钱包、排行榜、比赛场、反作弊和运营后台预留扩展空间。

## 2. 目标用户

### 2.1 休闲玩家

- 希望快速进入房间。
- 熟悉传统斗地主玩法。
- 需要清晰的轮到谁、倒计时、选牌、出牌和结算提示。

### 2.2 回访玩家

- 需要稳定的用户身份、战绩统计和断线重连。
- 刷新页面或短暂掉线后，希望继续当前牌局。

### 2.3 运营/管理员

- 需要观察在线房间、玩家连接和对局状态。
- 需要日志、牌局记录和基础风控调查数据。

### 2.4 AI 编程代理

- 需要从文档中明确知道每个模块的边界、输入输出、测试要求和验收标准。
- 必须可以一次只实现一个模块，而不是一次生成整个项目。

## 3. 产品范围

### 3.1 MVP 范围

MVP 包含：

- 游客登录，可扩展注册登录。
- 大厅、房间列表、快速开始。
- 创建房间、加入房间、准备状态。
- 三人经典斗地主。
- 叫地主/抢地主阶段。
- 出牌阶段，支持出牌、不出、提示。
- 基础机器人。
- 服务端权威游戏状态。
- WebSocket 实时同步。
- 可配置 TTL 的断线重连。
- 仅虚拟分数结算。
- 对局记录持久化。
- 基础日志和可观测性。

### 3.2 MVP 不包含

MVP 暂不实现：

- 真金钱玩法。
- 支付、提现、充值。
- 外部钱包。
- 复杂段位联赛。
- 比赛场。
- 语音聊天。
- 原生移动 App。
- 完整运营后台。
- 完整反作弊模型。

但系统架构必须为这些能力保留清晰扩展点。

## 4. 游戏模式

MVP 实现三人经典斗地主：

- 一副 54 张标准牌。
- 三名玩家。
- 地主 20 张牌。
- 两名农民各 17 张牌。
- 3 张底牌。
- 基础倍数模型。
- 炸弹和火箭翻倍。
- 任意一名玩家手牌出完后游戏结束。

详细规则见 [12-game-rules-engine.md](./12-game-rules-engine.md)。

## 5. 核心用户流程

### 5.1 游客快速开始

1. 用户打开网页。
2. 选择游客登录或自动游客进入。
3. 客户端调用登录 API。
4. 用户进入大厅。
5. 点击快速开始。
6. 服务端匹配等待房间或创建新房间。
7. 玩家进入房间并获得座位。
8. 三个座位就绪后开始游戏；无人补齐时机器人延迟补位。

验收标准：

- 首次用户 3 次点击内进入可玩的对局。
- 没有足够真人时，机器人可在配置延迟后补齐空位。

### 5.2 房间对局流程

1. 三名玩家进入房间。
2. 玩家准备。
3. 服务端洗牌和发牌。
4. 进入叫地主阶段。
5. 选出地主。
6. 底牌加入地主手牌。
7. 进入出牌阶段。
8. 当前玩家出牌或不出。
9. 服务端校验动作。
10. 有玩家手牌为空后游戏结束。
11. 广播结算。
12. 房间回到准备状态或关闭。

验收标准：

- 所有状态流转由服务端控制。
- 非法客户端动作被拒绝并记录日志。
- 所有客户端接收一致的公开状态。

### 5.3 断线重连流程

1. 玩家网络断开。
2. 服务端标记玩家离线，但保留座位。
3. 离线玩家轮到出牌时，根据策略由超时逻辑或机器人托管。
4. 玩家携带 token 重连。
5. 服务端恢复房间状态和该玩家私有手牌。
6. 玩家重新接管。

验收标准：

- 刷新页面可以恢复游戏。
- 私有手牌只恢复给座位所属玩家。
- 不允许通过重连泄漏其他玩家暗牌。

## 6. 功能需求

### 6.1 认证

MVP 认证：

- 游客登录。
- JWT access token。
- refresh token 可暂缓，但架构不能阻塞后续接入。

后续可扩展：

- 用户名密码。
- OAuth。
- 手机号登录。

### 6.2 大厅

大厅支持：

- 快速开始。
- 房间列表。
- 在线人数。
- 当前用户昵称和头像。

房间列表字段：

- 房间 ID。
- 模式。
- 当前人数。
- 房间状态。
- 底分。

### 6.3 匹配

快速开始策略：

1. 优先选择同模式、有空座的等待房间。
2. 没有可用房间则创建新房间。
3. 超过配置时间仍未满员时，机器人补位。

### 6.4 房间

房间支持：

- 加入。
- 游戏开始前离开。
- 准备。
- 游戏开始前真人可替换未锁定机器人。
- 状态广播。
- 表情聊天可作为可选功能。

### 6.5 游戏玩法

服务端处理：

- 洗牌。
- 发牌。
- 叫分。
- 地主选择。
- 底牌分配。
- 回合顺序。
- 出牌校验。
- 不出校验。
- 超时处理。
- 游戏结束。
- 结算。

### 6.6 机器人

机器人支持：

- 叫分决策。
- 出牌决策。
- 不出决策。
- 根据策略托管断线玩家的超时动作。

机器人设计见 [13-robot-ai-design.md](./13-robot-ai-design.md)。

### 6.7 记录

需要持久化：

- 对局元数据。
- 玩家快照。
- 初始牌。
- 叫分事件。
- 出牌事件。
- 结算。
- 时间戳。

安全要求：

- 对局记录可保存完整手牌。
- 普通玩家接口不得向无权限用户暴露隐藏牌。

## 7. 非功能需求

### 7.1 性能

MVP 目标：

- 局域网 WebSocket 动作往返低于 200 ms。
- 单次规则校验低于 5 ms。
- 开发基准中单进程支持至少 1,000 个空闲 WebSocket 连接。
- 单个房间的 tick/定时器不能阻塞其他房间。

### 7.2 可用性

MVP：

- 单后端实例可接受。
- 生产环境推荐 Redis 存储房间/会话短期状态。
- PostgreSQL 或 MySQL 持久化业务数据。

生产目标：

- 无状态 API 节点。
- WebSocket 网关节点。
- Redis 维护 session、房间注册和重连状态。
- 支持优雅停机。

### 7.3 安全

要求：

- 服务端权威状态。
- 不信任客户端提交的手牌、座位、回合身份。
- HTTP 受保护接口和 WebSocket 连接均校验 JWT。
- 所有动作都基于服务端房间状态校验。
- 对登录、房间动作、WebSocket 消息限流。
- 不记录 token。

### 7.4 公平性

要求：

- 洗牌使用加密安全随机数，或使用可审计的种子随机策略。
- 保存洗牌种子哈希或审计信息。
- 服务端独占发牌逻辑。
- 客户端只能获得合法的私有信息。

### 7.5 可观测性

必须记录：

- 登录。
- 加入/离开房间。
- 准备状态。
- 游戏开始。
- 叫分动作。
- 出牌动作。
- 非法动作。
- 断线/重连。
- 结算。

日志字段：

- trace_id。
- user_id。
- room_id。
- game_id。
- event_type。
- timestamp。

## 8. 成功指标

MVP 成功标准：

- 三个浏览器客户端可以完整打一局。
- 一个或多个机器人可替代缺失玩家。
- 对局中刷新页面可以恢复状态。
- 非法出牌会被拒绝。
- 已完成对局可由持久化事件重建。
- 单元测试覆盖核心牌型识别和出牌比较。

## 9. AI 开发政策

使用 AI 编程工具时：

- 每次只生成一个边界明确的模块。
- 以本文档体系为事实来源。
- 不得擅自发明游戏规则；需要先更新文档。
- 代码必须可测试。
- 每次规则变更都要补测试。
- 不得在 API 或 WebSocket 中泄漏隐藏牌。

详细规则见 [07-ai-coding-rules.md](./07-ai-coding-rules.md)。
